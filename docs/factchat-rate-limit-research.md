# FactChat 요청 제한 조사

- 조사일: 2026-09-11
- 목적: 통합 MCP의 2 vCPU 적용 후 FactChat 동시 요청 실패 원인 정리

## 테스트 조건

- MCP: 2 vCPU / 메모리 1 GiB / 인스턴스당 concurrency 40 / 최소 인스턴스 0
- 실제 FactChat 챗봇 API 사용: 교직원 51767, 학생 51766
- 교직원·학생 각각 독립 대화 40개 동시 요청
- 각 테스트 직전 사전 확인 요청 1개 실행
- 자동 재시도 없음
- 대화별 식별자로 실제 MCP 검색 호출 대조
- FactChat 동시 대화 40개와 MCP 동시 검색 40개는 다름: 모델의 검색 호출 시점이 분산됨

## 실측 결과

| 항목 | 교직원 | 학생 |
|---|---:|---:|
| 동시 요청 | 40개 | 40개 |
| 정상 완료 | 29개 | 29개 |
| FactChat HTTP 429 | 11개 | 11개 |
| 성공 요청 완료 중앙값 | 11.51초 | 13.32초 |
| 성공 요청 완료 p95 | 15.17초 | 16.92초 |

- 제한된 요청: 약 0.3초 만에 HTTP 429 반환
- 정상 완료 29개: 각 테스트 모두 목표 2 vCPU MCP 호출 확인
- 429 요청: 해당 식별자의 MCP 검색 기록 미관측
- 테스트 구간 MCP HTTP 오류: 없음
- 학생의 초기 HTTP 403은 접근 해제 후 해결됨: 이번 429와 별개

## 해석

- 확인된 사실: 이번 실패는 FactChat API 단계의 요청 제한으로 관측됨
- 가설 1 — 동시 요청 제한:
  - 두 챗봇 모두 같은 성공·실패 수를 보임
  - 다수 요청이 즉시 거절됨
- 가설 2 — 일정 시간 내 호출량 제한:
  - 사전 요청 1개 + 본 요청 성공 29개 = 30개
  - 사전 요청이 호출량 집계 구간에 포함됐을 가능성
- 아직 미확인:
  - 정확한 제한 수치와 집계 시간
  - 챗봇별·API 키별·계정별 제한 여부
  - 동시성 제한과 호출량 제한의 중복 적용 여부
- 결론: **동시 요청 제한이 의심되지만, 현재 결과만으로 확정 불가**
- 2 vCPU는 도달한 요청을 정상 처리했지만, 증설의 필수성·40개 전체 처리 여유까지 입증한 것은 아님

## 후속 검증 및 대응

- FactChat 측에 제한 단위·한도·초기화 주기 확인
- 충분한 대기 후 사전 요청 없이 동시 30개 테스트
- 별도 초기화 구간에서 순차 40개 테스트: 실제 요청 시각과 누적 수 기록
- 429 응답의 오류 코드·메시지·`Retry-After` 등 관련 헤더 수집
- 순차 요청도 같은 집계 구간에서 누적 30개 부근에 차단되면 호출량 제한 가능성 증가
- 순차 테스트가 길어 집계 구간을 넘으면 성공만으로 동시성 제한을 확정하지 않음
- 제한 확인 후 한도 상향 또는 호출 측 대기열·백오프 재시도 적용
- FactChat 자체 화면 사용 시 대기열·재시도는 FactChat 측 지원 필요
- MCP는 현재 2 vCPU / min 0 유지: CPU 추가 증설이나 min 1은 FactChat 429 해결책이 아님

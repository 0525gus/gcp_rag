# 통합 MCP 부하 테스트 — 2026-09-11 KST

현재 설정에서 40개 동시 요청의 갑작스러운 유입을 안정적으로 처리한다고 판단할 수 없다.
첫 증가 구간에서는 Cloud Run의 가용 인스턴스 부족으로 HTTP 500이 발생했다.
확장 이후 재검증은 모두 성공했으므로, 관측된 실패는 CPU 증설만으로 해결된다고 단정할 수 없다.

## 조건

- 운영 URI: `https://rag-mcp-42w47ff6ba-du.a.run.app/mcp`
- 리비전: `rag-mcp-unified-prod-0911`, 인스턴스당 1 vCPU / 1 GiB / concurrency 40 / min 0
- CS 교직원·학생 키를 교대로 사용, `top_k=5`, HTTP JSON-RPC `tools/call`
- 단계별 동시 작업자가 응답 후 다음 검색을 보내는 closed-loop 방식. 최대 10회/작업자.
- 매 질의에 고유한 검증 식별자를 추가해 정확히 같은 질의의 캐시 재사용을 피했다.
- 별도 재시도 없이 실제 오류를 집계. 오류 5건 이상이면 후속 요청 생성을 중단하고 진행 중 요청만 완료.
- 운영 설정·트래픽·권한·최소 인스턴스를 변경하지 않았다.

## 오류와 자동 확장

7건의 서버 로그는 모두 `The request was aborted because there was no available instance.`였다.
오류 직후 AUTOSCALING 사유의 새 인스턴스 6개가 시작했고, 약 10.6초 뒤 startup probe가 성공했다.
애플리케이션 검색 예외나 Vertex 쿼터 오류로 집계된 실패는 없었다.

수집한 분 단위 CPU 평균은 약 12.8–36.4%, 메모리 평균은 약 28.3–32.4%였다.
이는 인스턴스별 순간 최고 사용률이 아니므로 CPU 여유를 보장하는 근거로 사용하지 않는다.
Monitoring에는 수집 지연이 있으며, 짧게 확장된 인스턴스를 분 단위 instance_count만으로
설명할 수 없어 요청 로그의 instanceId별 집계도 확인했다.

Google은 이 HTTP 500에 대해 급격한 트래픽 증가, 긴 기동·처리 시간, Cloud Run의 일시적
요인을 점검하고 클라이언트의 지수 백오프 재시도를 권고한다.
[공식 문제 해결 문서](https://docs.cloud.google.com/run/docs/troubleshooting#abort-request)

## 판단

40은 설정된 인스턴스당 최대 동시 요청이며, 이번 테스트의 40은 서비스 전체로 보내는 동시 요청이다.
실제로 여러 인스턴스로 확장됐으므로 **인스턴스 한 개가 40개를 처리한 실험으로 해석하면 안 된다.**

현재 min 0 요구를 유지한다면 우선 기동 시간 단축, 검색 요청의 클라이언트 재시도,
더 낮은 인스턴스당 concurrency의 비교 측정을 검토해야 한다. concurrency를 낮춰도
처음 시작하는 인스턴스의 지연이 없어지지는 않는다. 2 vCPU의 효과는 동일한 급증 조건으로
별도 비교해야 하며 기존의 소규모 CPU 비교만으로 이번 실패가 해결된다고 판단하지 않는다.

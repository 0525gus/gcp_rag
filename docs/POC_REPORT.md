# 사내 문서 RAG 검색 시스템 — PoC 결과 보고

- 작성일: 2026. 7. 30.
- 대상: Google Drive 공유 드라이브 → Vertex AI RAG Engine → MCP 검색 전 구간
- 성격: 개략 보고. 각 항목의 상세 근거는 하단 [부속 문서](#ⅷ-부속-문서)에 있음

---

## Ⅰ. 요약

- □ **결론: PoC 목표는 달성함.** 실제 교내 공문 1,155건이 색인된 상태로 검색이
  동작하며, 외부 챗봇(FactChat)에서 MCP 커넥터로 사용 중임
- □ 일 배치 동기화가 무인으로 돌고 있으며 처리 실패는 0건임
- □ 검색 정확도는 **상위 5건 내 정답 89~94%**, 응답 지연 **1.3~1.4초**임
- □ 두 차례 전수 점검(7/28, 7/30)에서 **12건을 발견·조치**함
  - ○ 대부분 겉으로 드러나지 않는 잠복 결함이었음
- □ 다만 **학교 프로덕션 계정으로 옮기려면 선행 작업이 남아 있음**(Ⅶ장)

## Ⅱ. 구축 범위

### 1. 파이프라인

```
Cloud Scheduler (매일 00:00 KST)
  └─ Cloud Workflows
       ├─ Drive Changes API 델타 조회
       ├─ 형식별 분기
       │    HWP/HWPX      → 파서(rhwp) → Markdown
       │    Google 문서    → export
       │    PDF/DOCX/PPTX  → 복사 (한도 초과 PDF 는 페이지 분할)
       │    XLSX           → 셀을 Markdown 표로 변환
       ├─ GCS → Vertex RAG Engine 증분 색인
       ├─ 정합성 검증(reconcile)
       └─ 실패·누락 자동 회수

외부 챗봇 → Cloud Run MCP → RAG 검색
```

- □ **GCS 를 단일 진입점**으로 삼음. Drive 네이티브 커넥터는 쓰지 않음
  - ○ 사유: 형식별 전처리(한글 파일 변환, 표 추출, 분할)를 우리가 통제해야 함
- □ 상태는 Firestore 에 문서 단위로 보관하여 증분 동기화·복구가 가능함

### 2. 서비스 구성 (리전 `asia-northeast3`)

| 서비스 | 역할 |
|---|---|
| `rag-parser` | HWP/HWPX → Markdown 변환 |
| `rag-sync` | Drive/GCS/RAG 오케스트레이션 |
| `rag-mcp` | 검색 도구 제공 (MCP `search` / `answer`) |

## Ⅳ. 성능·품질 측정

### 1. 검색 정확도 (골든셋 100건, 2026-07-28)

| 기준 | 상위 1건 | 상위 3건 | 상위 5건 |
|---|---:|---:|---:|
| 정확히 그 문서 | 46% | 81% | **94%** |
| 같은 자료묶음(공문↔붙임) | 63% | 90% | 97% |

- □ 질의는 색인 문서에서 **무작위 추출한 뒤 본문을 읽고 작성**함
  - ○ 손으로 고르면 아는 문서만 골라 실제 분포를 못 봄
- □ **보수적으로는 상위 5건 89~94% 구간으로 읽어야 함**
  - ○ 표본 구간별로 hit@5 가 89% / 97% 로 갈리며, 낮은 쪽 구간에 정보량이 적은
    문서가 남아 있음
- □ 코퍼스에 없는 질문 6건은 **6건 모두 차단**함(엉뚱한 문서를 물어오지 않음)
- □ **한계**: 본문이 없는 문서(엑셀 스텁, 스캔 PDF 등 코퍼스의 약 24%)는
  측정에서 제외함. 그 유형은 파일명·경로로만 검색됨

### 2. 응답 지연

| 조건 | 지연 |
|---|---:|
| 기본(상위 5건) | 1.34초 |
| 상위 20건 | 1.44초 |

- □ 실사용에 충분한 수준임. 다만 최소 인스턴스가 0 이라 **첫 질의는 느림**

### 3. 한글 파서 선정 (135건 실측)

| 항목 | rhwp (채택) | kordoc (폐기) |
|---|---:|---:|
| 성공률 | 135/135 (100%) | 135/135 (100%) |
| 평균 소요 | **20.2 ms** | 341.7 ms |

- □ 합성 데이터가 아닌 **실제 접수 공문**으로 측정함

### 4. 청킹 크기

- □ 512 → 1024 로 변경함. 표가 청크 경계에서 잘리는 비율이 **16% → 6%** 로 감소함

## Ⅴ. 운영 안정성

두 차례 전수 점검을 실시함. **배포된 실제 환경과 데이터를 직접 조회**하는 방식으로,
코드 검토만으로는 드러나지 않는 항목을 확인함.

| 점검 | 발견·조치 | 유보 |
|---|---:|---:|
| 1차 (7/28) | 3건 | 8건 |
| 2차 (7/30) | 9건 | 6건 |

### 특기할 점

- □ **발견된 결함 대부분이 대시보드상 정상으로 보이는 상태에서 나왔음**
  - ○ 예: 일일 동기화가 3일간 실패 중이었으나 스케줄러 상태는 `ENABLED` 였음
  - ○ 예: 검색 API 가 3일간 무인증 공개 상태였으나 서비스는 정상 동작 중이었음
- □ 두 사례 모두 **실제 유실은 없었음**. 다만 조건이 겹쳤으면 조용히 누락되는
  구조였으므로, 잠복 결함으로 기록함
- □ 2차 점검에서는 **삭제한 문서의 원본이 GCS 에 잔존**하는 문제를 발견함
  (52건). 삭제 경로를 확장자 목록 방식에서 전수 조회 방식으로 교체함

### 아직 없는 것

- □ **알림이 하나도 없음**. 위 "3일간 실패"를 아무도 몰랐던 직접적 원인임
- □ 백업 장치 없음(Firestore PITR, GCS 버전관리 모두 비활성)
- □ 세 서비스가 프로젝트 편집자 권한으로 동작함(최소 권한 미적용)

## Ⅶ. 파일럿(학교 계정) 전환 시 필요한 작업

현 배포 스크립트는 **기존 리소스가 있다고 가정**하므로, 새 계정에서는 환경변수
수정만으로 동작하지 않음.

### 1. 스크립트가 만들어주지 않는 선행 리소스

| # | 대상 | 비고 |
|---|---|---|
| 1 | GCS 버킷 2개 | |
| 2 | Firestore 데이터베이스 | **Native 모드** 필요. 기본 Datastore 모드로는 동작 불가 |
| 3 | Vertex AI RAG 코퍼스 | 코퍼스를 먼저 만들어야 그 ID 로 환경변수를 채울 수 있음 |
| 4 | 서비스 간 호출 권한 | sync → parser |
| 5 | 검색 서비스 공개 설정 | 아래 2항 참고 |
| 6 | RAG 서비스 계정의 버킷 읽기 권한 | |
| 7 | **공유 드라이브에 서비스 계정 추가** | Drive 쪽 작업. 누락 시 동기화 전체 실패 |

### 2. 사전에 확인해야 할 위험

- □ **조직 정책이 외부 공개(`allUsers`)를 차단할 가능성이 높음.** 대학 조직에서
  흔한 설정이며, 차단된 경우 **현재의 챗봇 연동 방식(공개 URL + API 키)이
  성립하지 않음** → 인증 프록시 등 대안 설계가 필요함. **배포 착수 전에 확인할 것**
- □ 신규 프로젝트는 Vertex RAG 쿼터가 기본값이므로, 현재 운영에 적용된 삭제
  속도 설정을 그대로 쓰면 쿼터를 초과함(기본값으로 되돌릴 것)
- □ 검색 API 키는 새로 발급해야 하며, **서버만 바꾸면 챗봇 연동이 끊김** —
  클라이언트 커넥터 설정을 동시에 갱신해야 함

### 3. 권고

- □ 위 1~7 을 수행하는 **부트스트랩 스크립트를 먼저 만들 것.** 현재는 사람의
  기억에 의존하며, 실제로 1차 점검에서 발견된 사고 2건이 "스크립트를 거치지 않은
  수동 배포"에서 비롯됨

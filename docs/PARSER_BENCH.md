## Ⅳ. 채택 결정

### 1. 결론

- □ **rhwp (PyO3 네이티브) 채택**, kordoc 폐기

### 2. 근거

- ○ 표 인식률이 4.3배 높음 — 공문은 표 비중이 크므로 결정적 차이임
- ○ 처리 속도 17배 — 1,200건 전량 파싱 시 24초 vs 7분의 차이
- ○ 성공률·게이트 통과율은 실질적 차이 없음(각각 100%, 98.5% vs 99.3%)

### 3. 구현 반영

- □ `.hwp` → rhwp (PyO3 네이티브)
- □ `.hwpx` → python-hwpx (순수 파이썬)
  - ○ HWPX 는 ZIP+XML 구조라 네이티브 확장 없이 읽힘
  - ○ **rhwp 의 네이티브 ABI 리스크에서 분리**하는 것이 목적임
  - ○ HWPX 엔진 부재 시 rhwp 로 자동 대체(fallback)
- □ 관련 코드: [`services/parser/engine.py`](../services/parser/engine.py)

## Ⅶ. 표 렌더링 손실 측정 및 조치 (2026. 8. 5.)

- 대상 코퍼스: `sample/` (HWP 145건 + HWPX 1건)
- 재현: `python scripts/bench_hwp_corpus.py sample`

### 1. 문제

rhwp 렌더러의 두 성질이 마크다운 품질을 크게 깎고 있었음.

- □ **중첩 표(표 안의 표)를 렌더하지 않음**
  - ○ 부모 셀이 빈 `<td></td>` 로 나가고 내용이 통째로 사라짐
  - ○ 추출 가능 텍스트의 **13.2%(30,816자)** 가 이 경로로만 소실됨
  - ○ 사라진 것: 공문 **시행 문서번호**(`IR센터-162(2026.03.20.)`), **수신자 목록**,
    담당자 연락처, 그리고 일부 문서의 **본문 표 전체**
- □ **병합 셀이 하나라도 있으면 표 전체를 인라인 HTML 로 뱉음**
  - ○ 표 339개가 이 경로를 탔고, blob 이 마크다운의 **52.5%(226,616자)** 를 차지함
  - ○ 그중 **65.6%(148,572자)가 순수 태그** — 임베딩 토큰을 태우는 쓰레기
  - ○ 339개 중 **325개가 개행 없는 한 줄**(최장 4,337자) → 청커가 자를 지점이 없음
  - ○ 세로 병합된 분류 값이 첫 행에만 있어, 잘린 청크의 나머지 행은 소속을 잃음
- □ 여기에 G2 게이트의 기준값도 틀려 있었음
  - ○ `iter_blocks(scope="all")` 로 중첩 표까지 세어 기준값이 실제의 3배가 됨
  - ○ 렌더러가 표로 찍는 집합은 `scope="body", recurse=False` 임 — 145건 전부에서 일치함

### 2. 실측

동일 비교기(NFC + 공백 제거 후 부분문자열 포함)로 before/after 를 잼.

| 인라인 HTML 표 | 339개 (130/145 문서) | **0개** |
| 순수 태그 문자 | 148,572자 | **0자** |
| 마크다운 총 문자 | 391,865자 | **378,117자** (내용↑ 잡음↓ 순 -3.5%) |
| 표 행 라인 수 | 1,261줄 | **4,184줄** (표가 줄 단위로 쪼개져 청킹 가능) |
| 표 기준값 vs 렌더된 표 | 2,183 vs 716 | **716 vs 716** |
| G2 오탐(표 손실 판정) | 85 / 146건 | **0건** |

- □ `QG_MODE` 를 `reject` 나 `fallback` 으로 올렸다면 코퍼스의 58%가

  - ○ **표 없는 문서 무변경**: 새 IR 을 만들지 않고 원본을 그대로 반환

### 3. 조치

- □ 표를 렌더 전에 정규화함 (`_normalize_tables`)
  - ○ **병합 셀을 1x1 격자로 펼쳐** 렌더러를 GFM 경로로 돌림
    - rowspan: 값을 세로로 복제 → 청크가 행 단위로 잘려도 분류가 붙어 있음
    - colspan: 첫 칸에만 두고 나머지는 빈 칸 (같은 줄이라 정보 중복일 뿐)
    - 실측 표 2,181개 전부 좌표 충돌 0·빈칸 0. 그래도 충돌은 선착순, 구멍은 빈 셀로 방어함
  - ○ **중첩 표를 부모 셀 안 문단으로 접음** — 격자 펼침 덕에 모든 표가 GFM 경로라
    셀 수정이 그대로 출력에 반영됨
- □ 표 기준값을 `scope="body", recurse=False` 로 교정함
- □ `NESTED_TABLES_FLATTENED:<n>` / `MERGED_CELLS_EXPANDED:<n>` 경고로 관측 가능하게 함
- □ 관련 코드: [`services/parser/rhwp_parser.py`](../services/parser/rhwp_parser.py),
  테스트: [`tests/test_parser_nested_tables.py`](../tests/test_parser_nested_tables.py)

동작 근거는 추정이 아니라 **렌더러 소스**(`rhwp/ir/_view.py`)에서 확인함.

| 확인한 것 | 위치 | 함의 |
|---|---|---|
| `any(row_span>1 or col_span>1)` → `block.html` 반환 | `_md_table` | 병합이 없어야 GFM 경로 |
| 격자를 `rows`×`cols` 로 잡고 밖의 셀은 조용히 버림 | `_md_table` | 펼친 뒤 rows/cols 재계산 **필수** |
| 셀 안 `TableBlock` 은 아무것도 내지 않음 | `_md_cell_text` | 중첩 표 소실의 출처 |
| `cell.blocks` 를 읽기만 함 | `_md_table` | 복제 셀의 리스트 공유가 안전. 그래도 `list()` 로 뜸 |
| `TableBlock.text` 는 미사용, `html` 은 병합 표에서만 사용 | `_view.py` 전역 | 펼친 뒤 갱신 안 해도 마크다운 경로는 무해 |

### 4. 청크 크기 재검토가 필요함

- □ `scripts/analyze_chunking.py` 는 **GFM 표만 셈**(`find_gfm_tables`)
  - ○ 조치 전에는 병합 표 339개가 이 도구에 **아예 안 보였음** — 표 291개로 집계됨
  - ○ 즉 `rag_chunk_size=1024` 는 표의 46%만 본 표본으로 정한 값임.
    빠진 쪽이 하필 최악(한 줄 4,337자, 자를 수 없음)이었음
- □ 조치 후 같은 도구가 표 **630개**를 셈 — `291 + 339 = 630` 으로 정확히 일치함.
  안 보이던 병합 표가 빠짐없이 GFM 으로 전환됐다는 교차 검증임
- □ `chunk_size=1024` 의 표 절단율은 15%(291개 기준) → **27%(630개 기준)**
  - ○ 절단이 **늘어난 게 아니라 보이게 된 것**임. 조치 전 4,337자짜리 한 줄 blob 도
    983자 청크에 그대로 잘렸고, 다만 `|` 구조가 없어 도구가 세지 못했을 뿐임
- □ 재색인 비용이 있으므로 값 변경은 별도 판단 사항으로 남김

> 계수 주의: `find_gfm_tables`(630)는 연속된 `|` 줄 뭉치를 1개로 묶고,
> `count_markdown_tables`(716)는 GFM 구분행을 하나씩 셈. G2 정합성은 후자
> 기준이며 `_count_tables_in_ir` 와 145건 전부 일치함.

### 5. HWPX 경로의 별개 결함 — 셀 소실 + 표 구조 파손

rhwp 와 무관한, python-hwpx(`hwpx/tools/exporter.py`) 쪽 문제다. 결함 둘 다
**소스 확인 + 합성 문서 재현**으로 확정함.

**결함 1 — 셀 소실**

- □ `export_markdown` 이 표를 GFM 으로 내면서 **첫 행 길이로 뒤 행을 자름**
  (`padded[: len(header)]`)
- □ `_table_cells_text` 는 **rowspan/colspan 을 아예 무시**함 (`<tc>` 나열만)
- □ 둘이 겹치면 첫 행이 가로 병합된 표는 헤더가 1칸으로 잡혀 **나머지 열이 통째로 소실**

**결함 2 — 표 구조 파손**

- □ 셀 안 개행을 이스케이프하지 않음 (`"\n".join(cell_parts)`)
- □ 여러 줄 셀이 있으면 표 한 행이 여러 줄로 찢어져 GFM 표가 조각남
- □ **실제 문서에서 표 2개가 GFM 블록 6조각**으로 났고, 6조각 전부 열 수가 어긋나 있었음

**둘 다 표 개수는 맞아서 품질 게이트가 통과시킴** — 조용한 손상이었다.
특히 결함 2는 텍스트가 다 남아 있어 '손실' 판정으로는 잡히지 않는다.

조치 — `_repair_tables` ([`hwpx_parser.py`](../services/parser/hwpx_parser.py)):

1. 판정 두 축 — **셀 소실**(`export_text()` 기준, 헤더 절단을 안 함) +
   **구조 파손**(표 안 열 수 불균일 또는 구분행 없음)
2. **둘 다 없으면 원본 마크다운을 그대로 반환** → 멀쩡한 문서 출력 불변
3. 1단계: 찢어진 행을 구분행의 열 수 기준으로 도로 붙임 (rich 호출 없음)
4. 2단계: 여전히 소실이 있으면 `export_rich_markdown`(병합을 span 속성으로 보존)으로
   다시 뽑아 HTML 표를 격자 GFM 으로 폄
5. 어느 지표로도 나아지지 않으면 원본 유지 (개악 방지)
6. `HWPX_CELLS_RECOVERED:<n>` / `HWPX_TABLES_REPAIRED:<n>` 경고

검증 결과 (합성 8건 + 실제 1건):

| 문서 | 소실 | 깨진 표 | GFM 블록 | 출력 불변 |
|---|---|---|---|---|
| 정상 / A2:B2 / A1:A2 / B2:C3 | 0 → 0 | 0 → 0 | 1 → 1 | **예** |
| 3×3 A1:C1 (첫행 병합) | **4 → 0** | 0 → 0 | 1 → 1 | 복구 |
| 5×4 A1:D1 | **12 → 0** | 0 → 0 | 1 → 1 | 복구 |
| 셀 안 개행 | 0 → 0 | **2 → 0** | 2 → 1 | 복구 |
| 개행 + 병합 | **4 → 0** | **2 → 0** | 2 → 1 | 복구 |
| **실제 HWPX 1건** | 0 → 0 | **6 → 0** | **6 → 2** | 복구 |

- □ 실제 문서의 GFM 블록 6 → 2 는 `get_table_map()` 이 보고하는 표 개수 2 와 일치함
- □ 비용: 멀쩡한 문서 약 6ms(변동 없음), 복구가 필요한 문서 최대 33ms.
  HWPX 는 코퍼스의 ~3%라 총량 영향은 작음
- □ **빈도는 미확정**: HWPX 표본이 1건뿐임. 다만 **그 1건이 결함 2에 걸렸으므로
  결함 2는 드문 사례가 아닐 가능성이 높음.** 운영 26건의 경고 발생 건수로 확인할 것

### 7. XLSX 세로 병합 값 전파

세 번째 파서에서도 같은 부류의 문제를 확인했다.

- □ `shared/xlsx_md.py` 는 `read_only=True` 로 여는데, 이 모드는 `merged_cells` 가
  **항상 비어 있음** → 병합 처리가 아예 없었음
- □ 엑셀은 병합 시 좌상단에만 값을 남기므로 **아래 행은 분류를 잃음**
  (HWP 의 rowspan 과 같은 문제. 다만 값 자체가 사라지진 않아 심각도는 낮음)

실측 (`sample/` xlsx 17건):

| 항목 | 값 |
|---|---:|
| 변환 성공 | 13건 (실패 4건은 암호 걸린 OLE2) |
| **병합이 있는 문서** | **11 / 13 (85%)** |
| 병합 범위 | 157개 |
| **세로 병합** | **126개 (80%)** |

조치 — `_vertical_merges` + `_sheet_rows` 전파:

- □ `read_only=True` 를 유지한 채 **ZIP 에서 `<mergeCells>` 만 따로 읽음**
  (시트당 수십~수백 개라 싸고, `iterparse` + `elem.clear()` 로 본문을 안 쌓음)
- □ 시트 매칭은 `xl/workbook.xml` + rels 를 거침 — `sheetN.xml` 의 N 은 표시 순서와 무관
- □ 세로 병합만 전파. 가로 병합은 지금도 좌상단에만 값이 있어 같은 줄 안 중복일 뿐

검증:

| 항목 | 결과 |
|---|---|
| ZIP 방식 vs openpyxl(`read_only=False`) 병합 범위 | **12/12 파일 완전 일치** |
| openpyxl 이 열지 못한 파일 | ZIP 방식은 **성공** (1건) |
| 전파 대상 행 419 → 채워진 셀 | **419** (1:1, 과잉 0) |
| 값 손실 | **0** |
| 병합 없는 문서 9건 출력 | **완전 불변** |

- □ 부수 수정: `scripts/bench_xlsx_md.py` 가 `glob`(최상위만)이라 하위 디렉터리
  코퍼스를 **조용히 0건으로 보고**했음 → `rglob` 으로 교정
  (`analyze_chunking` 사각지대와 같은 부류의 계측 오류)

### 9. 남은 제약

- □ 중첩 표는 문단으로 접히므로 **행/열 구조는 잃음**(내용만 보존)
- □ 펼친 뒤 `TableBlock.html` / `.text` 는 `cells` 와 어긋난 채로 남음.
  이 파이프라인은 `to_markdown()` 만 쓰므로 무해하나, **`to_html()` 을 쓰게 되면
  병합 표가 옛 HTML(중첩 표 내용 없음)로 나옴**
- □ GFM 은 첫 행이 무조건 헤더가 됨. 병합 표의 첫 행이 제목행이면 그것이 헤더로 감
- □ 검증 코퍼스가 `sample/` 146건임. 운영 코퍼스(892건)에서는 미측정 —
  좌표 충돌·격자 구멍은 여기 2,181개 표에서 0건이었으나 방어 코드로만 대비함
- □ **이미지 안 텍스트는 여전히 미회수** — 145건 중 96건에 이미지 212개가 있고
  캡션이 달린 것은 1개뿐임. Document AI 폴백은 유료라 최후 수단으로 남겨 둠
- □ **마크다운 헤딩이 0개** — 145건 전부에서 `#` 헤딩이 생성되지 않음.
  개요 마커는 1,084줄 있음(`□` 139, `○` 83, `◦` 82, `1./2./3.` 333, `가./나./다.` 213).
  헤딩으로 승격할지는 청킹 전략과 함께 결정할 사안임
- □ 자간 벌린 제목 11줄(`공 적 조 서`), 사제 글꼴 PUA 문자 20개(6문서),
  빈 표 행 76줄 — 계량은 했으나 영향이 작아 미조치
- □ HWPX 의 `get_table_map()` 이 중첩 표를 어떻게 세는지는 표본 1건이라 미검증
- □ HWPX 복구 경로는 `**` 강조 마크업이 섞인 `export_rich_markdown` 출력을 쓴다.
  손실이 있는 문서에서만 타므로 영향 범위는 좁지만, 그 문서의 산문에는 `**` 가 남음

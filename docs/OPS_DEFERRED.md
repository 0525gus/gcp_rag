# 운영 전환 시 처리할 것 (PoC 범위 밖)

PoC 로 돌리는 동안은 넘어가기로 한 항목들. **실제 운영에 올리기 전에**
여기 있는 것들을 한 번씩 훑을 것.

각 항목에 "왜 지금은 괜찮은가"와 "언제 문제가 되는가"를 같이 적었다.
지금 괜찮다는 판단의 근거가 사라지면 그때가 처리할 시점이다.

---

## 1. 시크릿이 평문 환경변수

`MCP_API_KEY` 가 Cloud Run 환경변수에 평문으로 들어간다. Secret Manager 를
쓰지 않는다(프로젝트에 시크릿 0개).

- **지금 괜찮은 이유**: 키 하나뿐이고, 프로젝트 IAM 을 가진 사람만 읽을 수 있다
- **문제가 되는 시점**: 프로젝트 뷰어 권한을 외부에 주는 순간. `roles/viewer`
  만 있어도 `gcloud run services describe` 로 키가 그대로 보인다
- **조치**: Secret Manager 로 옮기고 `--set-secrets` 로 주입

### 곁들여: 키가 배포에서 사라지는 구조

`MCP_API_KEY` 는 리비전 00005(7/25)에서 조용히 유실됐고 00013 까지 8개
리비전 동안 없는 채로 떠 있었다. 그동안 `allUsers` invoker 와 겹쳐
**인증 없이 코퍼스 전체가 검색됐다**(2026-07-28 복구, `rag-mcp-00014`).

배포 스크립트([`deploy.ps1`](../scripts/deploy.ps1) /
[`deploy_mcp.ps1`](../scripts/deploy_mcp.ps1))는 키를 필수로 강제한다. 문제는
그 스크립트를 **안 거치고** `gcloud run services update` 를 직접 쓸 때
`--set-env-vars` 가 기존 값을 통째로 갈아버리는 것이다.

- **조치**: 키를 Secret Manager 로 옮기면 이 사고 유형 자체가 사라진다
  (시크릿 참조는 env 갱신과 별개로 유지됨). 그 전까지는 `update` 시
  `--update-env-vars`(누적)만 쓰고 `--set-env-vars`(치환)를 쓰지 말 것

## 2. 알림이 하나도 없다

```
알림 정책     0
로그 기반 지표 0
알림 채널     0
```

- **지금 괜찮은 이유**: 사람이 직접 돌려보며 쓰는 단계
- **문제가 되는 시점**: 이미 한 번 겪었다. 일일 동기화 스케줄러가
  2026-07-25 부터 **3일간 400 으로 죽어 있었는데 아무도 몰랐다.**
  대시보드는 전부 초록불이었다(스케줄러 ENABLED, 워크플로 존재, Cloud Run 정상).
  마침 그 기간에 신규 문서가 없어서 유실은 없었지만, 있었다면 조용히 빠졌다
- **조치**: 최소 두 개
  - Cloud Scheduler 실행 실패 → 알림
  - `rag-sync` / `rag-mcp` 5xx 비율 → 알림

  둘 다 로그 기반 지표 + 정책 하나씩이면 된다

## 3. 백업·복구 장치 없음

```
Firestore  PITR 비활성 / 삭제보호 비활성
GCS        raw·normalized 둘 다 버전관리 없음
```

- **지금 괜찮은 이유**: Drive 가 원본이라 최악의 경우 전량 재수집이 가능하다
  (다만 892건 HWP 재파싱 + 재색인이라 시간이 든다)
- **문제가 되는 시점**: `doc_state` 를 날리면 무엇이 색인됐는지 알 방법이
  없어져 증분 동기화가 처음부터 다시 돈다. GCS 버전관리가 없어 정규화
  산출물을 덮어쓰면 되돌릴 수 없다 — 이번 머리말 마이그레이션 때는
  로컬에 원본을 받아둬서 롤백 경로를 수동으로 확보했다
- **조치**: Firestore 삭제보호 켜기(플래그 하나), PITR 켜기,
  normalized 버킷 버전관리 켜기

## 4. 드라이브 파일 위생

무작위 표본 50건 실측 기준:

| | 건수 | 비율 |
|---|---:|---:|
| 파일명이 겹치는 사본 (`폴더 (1)` 등) | 122 / 1,211 | 10.1% |
| 내용 없는 xlsx (스텁만 색인) | 116 / 1,211 | 9.6% |
| 텍스트층 없는 PDF (스캔본) | 표본 50 중 3 | ~6% |
| 초안·의견수렴본 | 201 / 1,211 | 16.6% |

- **지금 괜찮은 이유**: 검색 품질에 미치는 영향을 실측했다. 사본 제거의
  hit@1 개선은 **+1건**에 그쳤고, 내용 없는 문서를 빼도 점수는 오히려
  34% → 32% 로 내려갔다. 즉 **점수 문제가 아니다**
- **문제가 되는 시점**: 사용자가 "최신본"을 물을 때. 초안과 확정본이 같이
  걸리면 LLM 이 어느 쪽을 인용할지 통제할 수 없다
- **조치**: 드라이브 정리는 사람 손이 필요하다. 코드로 할 수 있는 건
  경로 패턴(`(1)`, `개정(안)`, `의견수렴`) 기반 감점 정도

## 5. 암호 걸린 xlsx 27건은 여전히 못 읽는다

xlsx 본문 파싱은 [`shared/xlsx_md.py`](../shared/xlsx_md.py) 로 **해결했다**(116건 중
89건). 남은 27건은 파일에 암호가 걸려 있어 어떤 도구로도 열 수 없다.

발견 경위가 기록해둘 만하다. 매직바이트가 `D0CF11E0` 라 처음에는 구형 `.xls`
로 판단했으나, OLE2 스트림을 열어보니 `EncryptedPackage`/`EncryptionInfo` 였다.
**암호화된 OOXML 은 OLE2 로 감싸여 구형 이진 포맷과 매직바이트가 같다**(MS-OFFCRYPTO).
확장자로도 매직바이트로도 구분되지 않는다.

- **지금 괜찮은 이유**: 파일명·경로 사이드카로는 여전히 검색된다. 그리고 작성자가
  일부러 암호를 걸었다는 건 **색인되지 않는 편이 맞는 문서**라는 신호에 가깝다
- **문제가 되는 시점**: 그 27건 안의 내용을 물을 때. 지금은 본문이 없다는 사실이
  로그(`xlsx→md 실패`)에만 남고 사용자에게는 안 보인다
- **조치**: 암호를 아는 경우에만 가능하다. 대량 해독은 범위 밖이므로,
  필요해지면 **문서 소유자에게 암호 해제를 요청**하는 절차가 현실적이다

### 곁들여: 구형 `.xls` 는 코퍼스에 없다

`.xls` 확장자 0건, 매직바이트로 위장한 것도 0건이다. 그래서 `xlrd` 나
LibreOffice 변환 경로는 **들이지 않았다**. `.doc`/`.ppt` 도 마찬가지로 0건이라,
구형 오피스 대응은 실물이 유입되는 시점에 판단하면 된다.

## 6. raw 버킷 IAM 미분리

`raw` 와 `normalized` 의 IAM 이 바이트 단위로 동일하다(프로젝트 기본 역할만).
자세한 내용은 [`STORAGE_LAYOUT.md`](./STORAGE_LAYOUT.md).

- **문제가 되는 시점**: raw 에는 원본 공문이 그대로 있다(학사경고자 명단,
  인사발령 등). RAG Engine 서비스 에이전트가 읽을 이유가 없는데 막혀 있지도 않다
- **조치**: raw 에서 RAG 서비스 에이전트 읽기 권한 명시적 배제

## 7. 콜드스타트

`rag-mcp` / `rag-sync` / `rag-parser` 모두 `min-instances=0`.

- **지금 괜찮은 이유**: 내부 검증 단계라 첫 질의가 느려도 문제없다
- **문제가 되는 시점**: FactChat 사용자가 늘어 첫 응답 지연이 체감될 때.
  MCP 커넥터에 타임아웃이 있으면 콜드스타트가 그걸 넘길 수 있다
- **조치**: `rag-mcp` 만 `min-instances=1`. sync/parser 는 배치라 0 이 맞다

## 8. 한도 초과 큐를 비우는 코드가 없다

`doc_split_queue` 는 **쓰기 전용**이다. 적재는
[`firestore_state.py`](../shared/firestore_state.py) `enqueue_split` 한 곳뿐이고,
읽는 코드는 레포에 없다. 이름이 "분할 대기 큐"라 곧 처리될 것처럼 읽히지만
실질은 **한도 초과 전용 DLQ** 다. `/sync/retry-failed` 가 FAILED 상태로 다시
집어가긴 하나 같은 크기 게이트에 다시 걸려 `stillFailed` 로 돌아온다.

- **지금 괜찮은 이유**: 큐가 **0건**이고, 비는 게 우연이 아니다. 텍스트 계열
  실측 최대가 64KB 로 10MB 한도의 0.6% 라 구조적으로 닿지 않는다
  (근거: [`DEV_SPEC.md`](./DEV_SPEC.md) "2. 크기 한도 대응")
- **문제가 되는 시점**: 이미지가 많은 PPTX 나 큰 XLSX 가 들어올 때.
  조용히 색인에서 빠지는데 큐를 보는 사람이 없으면 모른다
- **조치**: 분할이 아니다. 그런 파일은 10MB 가 이미지 용량이라 쪼개도 텍스트가
  안 늘어난다. (1) 큐 적재 시 로그 기반 알림(→ 2번 항목과 같이),
  (2) PPTX/XLSX 텍스트 추출 경로 추가(→ 5번 항목과 같이 판단)

## 10. 세 서비스가 프로젝트 Editor 권한으로 돈다 〔심각〕

```
rag-sync / rag-mcp / rag-parser
  → 327280624781-compute@developer.gserviceaccount.com
  → roles/editor
```

전용 서비스계정이 없어 세 서비스 모두 기본 Compute Engine 계정을 쓴다. 그
계정은 프로젝트 **Editor** 다. 인터넷에 노출된 `rag-mcp` 도 마찬가지다.

1차 점검(`OPS_AUDIT.md` Ⅲ.4)은 접근제어를 "누가 호출할 수 있나"(ingress)만
봤고 "무슨 권한으로 도나"(runtime identity)는 보지 않았다. 6번 항목도 버킷
IAM 만 다룬다. **두 문서 모두의 사각지대였다.**

- **지금 괜찮은 이유**: API 키만으로는 코드 실행이 안 되므로 키가 새도 검색
  이상은 못 한다. 즉 직접 악용 경로가 없다
- **문제가 되는 시점**: 컨테이너 안에서 임의 코드가 도는 순간. 그 경로는
  의존성이다 — 2026-07-30 기준 `starlette`/`uvicorn`/`google-*` 이 모두
  `>=` 만 걸려 있었고(같은 날 메이저 상한 추가), 공급망 사고 하나가
  Firestore·GCS·코퍼스 삭제 권한을 그대로 얻는다. Editor 는 그 폭발 반경을
  프로젝트 전체로 만든다
- **조치**: 서비스별 전용 SA + 최소 권한. 우선순위는 `rag-mcp` 다(유일하게
  공개). 필요 권한은 코드에서 그대로 읽힌다

  | 서비스 | 필요 권한 |
  |---|---|
  | rag-mcp | Vertex RAG 조회, Firestore 읽기 |
  | rag-sync | + Firestore 쓰기, GCS 읽기/쓰기, Vertex RAG import/delete, parser 호출 |
  | rag-parser | GCS 읽기/쓰기, Firestore 읽기 |

## 11. 품질 게이트 3개 중 2개가 발동하지 않는다

판정 로직은 있으나 파서가 입력값을 채우지 않아 구조적으로 발동 불가다.

| 게이트 | 상태 | 이유 |
|---|---|---|
| G1 밀도 | 살아 있음 | |
| G2 표 | **발동 불가** | `table_cell_failures` 를 채우는 코드가 없음(항상 0) |
| G3 이미지 | **발동 불가** | `image_area_ratio` 를 채우는 코드가 없음(항상 0.0) |
| EMPTY_TEXT | 살아 있음 | |

`QG_TABLE_FAIL_RATIO=0.3` / `QG_IMAGE_RATIO=0.5` 는 `.env.example` 에도 있고
운영에도 들어가 있지만 아무것도 제어하지 않는다.

- **지금 괜찮은 이유**: `QG_MODE=log` 라 게이트가 색인을 막지 않는다. 즉
  발동 여부가 파이프라인 동작을 바꾸지 않는다
- **문제가 되는 시점**: 이미 대가를 치렀다. G3 은 "밀도가 낮은 게 이미지가
  많아서인지 파싱이 실패해서인지"를 가르는 게이트다. 그게 죽어 있어 구분을
  G1 혼자 져야 했고, 이미지 많은 공문의 오탐을 막느라 G1 임계값을 0.0005 까지
  낮췄다([`config.py`](../shared/config.py) 주석). **진짜 파싱 실패를 잡을
  여력도 같이 잃었다.** `QG_MODE=reject` 로 전환하려면 이걸 먼저 풀어야 한다
- **조치**: 두 계측을 파서에 추가(HWP/HWPX 에서 이미지 면적, 표 셀 추출 실패
  수)하고 `PARSER_BENCH.md` 를 다시 재는 것. 아니면 무효한 설정값 두 개를
  걷어내 혼동을 없애는 것 — 둘 중 하나는 해야 한다
- 코드 쪽 사실은 [`quality_gate.py`](../services/parser/quality_gate.py)
  머리말에 적어 두었다

## 12. 검색 다양성이 파일 단위라 게시글 하나가 결과를 독점할 수 있다

`postprocess_hits` 는 fileId 단위로 다양성을 지킨다. 그런데 이 코퍼스의
의미 단위는 **자료묶음(게시글/문서접수 건)** 이다.

```
INDEXED 1,155건 / bundle 369개   = bundle 당 평균 3.1개
bundle 당 파일 수 중앙값          2개
2개 이상인 bundle                 296 / 369 (80.2%)
최다                              28개  '규정 제·개정 및 폐지 안내'
                                  27개  '규정 제·개정 및 폐지에 대한 의견 수렴 안내'
                                  27개  '규정 제·개정에 대한 의견 수렴 안내'
```

실측: `수강신청 정정기간` 질의의 top_k=5 결과 중 3건이 같은 게시글
(`147294_...`)의 다른 첨부였다. 즉 문서 5건처럼 보이지만 실제로는 게시글
3건이다.

- **지금 괜찮은 이유**: 같은 게시글의 첨부는 실제로 서로 관련이 있어, 붙어
  나오는 게 늘 손해는 아니다
- **문제가 되는 시점**: 규정 질의. 상위 bundle 3개가 하필 4번 항목이 지적한
  `의견 수렴`·`초안` 류다. 확정본 대신 의견수렴본 첨부 여러 개가 결과를
  채우면 LLM 이 초안을 인용한다
- **조치**: `max_chunks_per_file` 과 같은 모양의 bundle 상한을 넣는 것.
  다만 **검색 순위를 바꾸는 변경이라 골든 100 으로 먼저 재야 한다**
  ([`GOLDEN_EVAL.md`](./GOLDEN_EVAL.md), `scripts/eval_golden.py`).
  측정 없이 켜지 말 것

## 13. 재질의 폭주 — 지시문으로는 잡히지 않았다

툴 설명에 "같은 의도로 다시 검색하지 마세요, 한 질문에는 원칙적으로 한 번만"
을 넣었는데(커밋 `4eaeea8`) 지켜지지 않는다. 운영 로그 실측(7/29~7/30):

```
총 search 호출   50
고유 질의        37       ← 13회(26%)가 바이트 단위 동일한 재질의
최다 반복        8회      'LMS 시스템 AI 기능 수요조사 내용 목적 조사 항목 결과 일정'
```

50회가 사실상 질문 하나에 대한 것이었고 18분간 5차례 버스트로 나갔다(21초에
8회가 몰린 구간 포함). 응답이 top_k=10~20 에서 60KB 라 한 질문에 1MB 넘는
컨텍스트가 쌓인다.

- **완화됨**: 같은 `(query, top_k, drive_id)` 에 대한 짧은 TTL 응답 캐시를
  넣었다(`SEARCH_CACHE_TTL_SECONDS`, 기본 60초). 반환값이 완전히 같아 호출측
  동작은 달라지지 않는다. 동일 문자열 반복분은 이걸로 잡힌다
- **남은 문제**: 표현만 바꾼 재질의는 캐시가 못 잡는다. 위 50회 중 다수가
  그쪽이다. 그리고 28회를 시도해도 답을 못 찾았다는 건 **코퍼스에 그 문서가
  없다**는 뜻인데, `uncoveredTerms`/`coverage` 신호가 "확인되지 않음" 결론으로
  이어지지 못하고 있다(5번 항목의 "9회 재질의 끝에 실패"와 같은 모양)
- **문제가 되는 시점**: 비용과 지연. 인스턴스가 최대 20개까지 뜨고 Vertex
  검색은 호출당 과금이다
- **조치**: 캐시는 임시방편이다. 근본은 (1) 없는 것을 없다고 말하게 하는
  응답 설계, (2) 호출측(FactChat) 프롬프트에서 재질의 억제 — 서버가 강제할
  수 없는 영역이라 클라이언트 설정과 함께 봐야 한다

## 14. 운영에만 손으로 들어간 설정값

배포 스크립트에 없던 값이 운영에 손으로 들어가 있었다. `--set-env-vars` 는
치환이므로 스크립트를 돌리면 사라진다. 같은 날 스크립트에 등록해 두었으나,
**아직 반대로 스크립트 기본값이 운영과 다른 것이 남아 있다.**

| 대상 | 운영 | 스크립트 기본 | 판단 필요 |
|---|---|---|---|
| `SEARCH_FETCH_MULTIPLIER` (rag-mcp) | 6 | 3 | ✅ |
| `RAG_DELETE_CONCURRENCY` (rag-sync) | 4 | 1 | |
| `RAG_DELETE_PACING_SECONDS` (rag-sync) | 0.6 | 1.1 | |
| `--concurrency` (rag-parser) | **160** | 8 | ✅ |

- **`SEARCH_FETCH_MULTIPLIER=6` 은 문서화된 불변식을 깬다.**
  [`config.py`](../shared/config.py) 는
  `search_fetch_max >= search_top_k_max * search_fetch_multiplier` 를 지키라고
  적었는데 운영은 `60 < 20 × 6 = 120` 이다. `top_k<=10` 까지는 무해하지만 그
  이상에서 여유분이 조용히 잘린다. `SEARCH_FETCH_MAX=100`(Vertex 상한)으로
  올릴지 `SEARCH_TOP_K_MAX` 를 내릴지는 실측한 사람이 정해야 한다
- **`rag-parser --concurrency=160` 은 위험하다.** 파서는 HWP 원본을 통째로
  메모리에 올리고 네이티브 확장으로 파싱하는데 컨테이너는 2Gi 다. 지금
  안전한 건 `RAW_UPLOAD_CONCURRENCY=8` 이 실효 동시성을 묶고 워크플로가
  순차라서일 뿐이다. 운영에도 반영할 것:
  `gcloud run services update rag-parser --region=asia-northeast3 --concurrency=8`
- **조치**: 위 두 개는 운영 값을 바꿔야 한다. 아래 두 개(삭제 페이싱)는
  쿼터를 올렸다면 운영 값이 맞으니 스크립트 기본값을 운영에 맞출 것

## 15. 자잘한 것

- **워크플로 델타 경로의 색인 상한 ~1,050 URI.** `index_batch_size` 인자를
  받지만 델타 경로는 무시하고 `pending_uris` 를 한 번에 보낸다.
  `import_from_gcs` 가 내부적으로 25개씩 쪼개 호출당 ~21초이므로 timeout
  900초 안에 약 42회 = 1,050 URI 가 한계다. 하루 100건 수준이면 무해하다
- **`sync_jobs` 컬렉션 미정리.** 현재 8건. 재색인 잡 기록이 계속 쌓인다
- **`doc_state` 의 DELETED 튜플이 영구 잔존.** 현재 100건. 복구된 파일을
  다시 색인하려면 상태가 남아 있어야 해서 의도된 것이지만, 무한히 쌓인다
- **`cleanup.py` 의 `_PAGE_NO` 정규식이 `mix` 를 페이지번호로 오인한다.**
  로마숫자 매칭이 m+x+i 로 붙는다. 한글 공문에 "mix" 만 있는 줄이 나올 일이
  없어 실해는 없다
